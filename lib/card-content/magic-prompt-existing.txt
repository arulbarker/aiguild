```
│

│   → catat sebagai rekomendasi untuk ~/.claude/templates/
│   → jangan pindahkan sendiri, laporkan ke user dulu
│
├── User / customer / end-user butuh
│   → docs/nama-file.md di ROOT project (bukan di .claude/)
```

Kalau satu file berisi campuran topik → rekomendasikan untuk dipecah, konfirmasi dulu.

Laporkan hasil audit lengkap ini. BERHENTI dan tunggu konfirmasi sebelum lanjut.

### Tentang ideas-backlog.md


### .claude/rules.md
### Standar profesional inti (WAJIB ditulis apa adanya ke rules.md, jangan diubah)
Tulis blok berikut ke bagian atas rules.md persis seperti ini:

```markdown
## Standar inti (tidak bisa dikalahkan aturan lain)

### Local-first (lokal dulu, deploy kemudian)
Berlaku SEMUA platform. Bangun & sempurnakan di lokal sampai mulus,
baru deploy ke prod. Prod tempat penyajian, bukan eksperimen. Jangan kebalik.
Pengecualian GAS: tidak ada "lokal" — pakai 2 deployment (dev+prod) + 2 spreadsheet (dev+prod).
App pribadi/internal sederhana GAS boleh prod-saja (asal tidak ada data orang lain & risiko kecil).
TIDAK relevan untuk GAS: CI/CD, Prisma/migrasi SQL, npm run dev, Vitest.
TETAP berlaku untuk GAS: git (version control + backup), Chrome DevTools (debug bareng), keamanan, performa GAS.

### Git
- Branch utama (master/main) itu SUCI — dilarang commit/push langsung
- Selalu buat branch baru: feat/ fix/ docs/ chore/
- Conventional commits. Commit tiap perubahan berarti
- STOP setelah push — merge HANYA dengan perintah eksplisit user
- Setelah merge berhasil → tawarkan hapus branch yang sudah selesai (lokal + remote).
  Syarat: branch benar-benar sudah ter-merge. Jangan hapus yang belum di-merge.

### Keamanan (prioritas tertinggi)
- Rahasia (token/API key/kredensial) DILARANG di kode & file .md — pakai .env + placeholder
- Semua pintu masuk data (form, API, webhook, upload) wajib divalidasi
- Error message tidak boleh bocorkan detail internal
- Least privilege: tiap komponen akses seminimal yang dibutuhkan
- Identifikasi stack project ini → terapkan best practice keamanannya
  (contoh: Supabase = RLS wajib; VPS = firewall + SSH key + DB tidak publik;
  mobile = API key jangan hardcode; webhook = verifikasi signature)
- Temuan security review tidak boleh di-skip tanpa keputusan eksplisit user

### Testing (workflow 3 lapis — era AI)
Filosofi: test yang KALAU RUSAK paling bikin celaka, bukan semua.
- Lapis 1 — AI manual check: Claude + Chrome DevTools real-time, untuk dev harian (valid sbg E2E manual)
- Lapis 2 — Automated test HANYA fungsi kritis: hitung uang, auth, pembayaran, upload file
  Alat: Vitest (JS/TS), pytest (Python), JUnit (Kotlin), manual editor (GAS)
  Jangan test hal kosmetik (warna, teks statis)
- Lapis 3 — CI/CD: GitHub Actions jalankan test otomatis tiap push. WAJIB semua web app. Gratis.
  Test gagal → merge diblokir
- Smoke test wajib sebelum setiap push

### Monitoring
- PostHog + Sentry wajib SEBELUM launch ke user nyata —
  tapi bukan blocker saat development/prototype

### Environment dev vs prod (untuk app dengan database)
- Dev (lokal) dan prod (server) terpisah total: app, database, Docker, kredensial
- DILARANG menyentuh database/environment PROD tanpa perintah eksplisit user
- Kredensial prod tidak pernah di laptop — hidup di env server
- Migrasi database: test di dev dulu, ke prod hanya dengan perintah eksplisit + backup
- Default Claude selalu kerja di dev — kalau ragu environment mana, tanya dulu
- Prisma/ORM: db push untuk fase eksperimen (belum ada user), beralih ke migrate SEBELUM
  prod punya data. Jangan pakai db push terus sampai prod berdata (Prisma minta reset)
- Kapan tanya soal DB: dev = bebas; prod + perubahan aman (kolom nullable/tabel baru) = jalan;
  prod + berbahaya (reset/drop/ubah tipe) = STOP + WAJIB tanya + ingatkan backup

### Aturan prioritas saat konflik
1. Perintah eksplisit user saat ini (terkuat)
2. rules.md ini
3. CLAUDE.md project
4. CLAUDE.md global (kalau ada)
Kecuali: standar inti di atas tidak bisa dikalahkan apapun

### Anti-stuck
Jangan jadikan aturan apapun sebagai blocker yang bikin berhenti kerja.
Kalau aturan tidak bisa dipenuhi karena keterbatasan platform →
laporkan + tawarkan alternatif, terus kerja.
```

```markdown
# Skill: dev-server

## Kapan aktif
Saat mulai menjalankan/mengecek run dev web app ini.

## Penting: user biasanya sudah jalankan npm run dev sendiri
User sering menjalankan npm run dev sendiri sebagai preview live saat vibe coding.
Jadi SEBELUM menjalankan dev server, cek dulu:
1. Apakah dev server sudah jalan? (cek port 3000/sejenisnya, atau tanya user singkat)

## Cara kerja default
- Pastikan dulu server belum jalan (lihat di atas), baru jalankan kalau perlu
- Buka via Chrome DevTools MCP — supaya Claude dan user lihat layar yang SAMA real-time
- Gunakan untuk: cek hasil perubahan langsung, debug error runtime, inspect console,
  cek network request, lihat tampilan UI
- Ini live server interaktif: user lihat, Claude lihat, bisa debug bareng

## Yang TIDAK dilakukan
- Jangan jalankan Playwright otomatis untuk dev biasa — itu untuk E2E test terstruktur,
  dipakai HANYA kalau user minta eksplisit
- GAS: Chrome DevTools tetap dipakai (ada HTML frontend), TAPI tanpa npm run dev — preview lewat deployment URL dev
- Jangan pakai Chrome DevTools untuk project non-web murni (desktop, mobile)

## Beda Chrome DevTools vs Playwright (biar tidak ketuker)
- Chrome DevTools = nonton bareng real-time, debug interaktif → DEFAULT untuk dev
- Playwright = robot QA otomatis di background → manual saja, kalau user minta
```

```markdown
# Skill: vps-setup

## Prinsip
Local-first. Kuasai di lokal sampai mulus DULU, baru naik ke VPS.

## 4 Tahap (jangan loncat)
1. LOKAL: bikin docker-compose.dev.yml → app + DB dev jalan di localhost sempurna
2. FILE PROD: bikin docker-compose.prod.yml + .env.prod.example (struktur sama dev, beda config)

JANGAN "hapus semua lalu isi ulang" (deleteMany+create) — hapus data user di prod.
Pakai upsert: data lama diupdate (id dipertahankan), data baru ditambah, data user aman.
```

### .claude/skills/gas-performance.md
Buat HANYA jika project ini app GAS (Google Apps Script) dengan banyak layar/menu.
Kalau bukan GAS, LEWATI file ini.

Isi dengan instruksi ini persis:

```markdown
# Skill: gas-performance

## Kapan aktif
Saat bikin/edit frontend app GAS yang punya banyak layar/menu.

## Struktur file (cek tujuan project dulu)
- GAS untuk DIJUAL sebagai template → file tunggal: Code.gs + index.html saja.
  Pembeli non-teknis, copy-paste 2 file lebih mudah. Di dalam file pakai pemisah
  section komentar yang jelas (// === 1. KONFIGURASI === dst).
- GAS untuk pakai sendiri/kompleks → boleh pisah file (Code.gs, Auth.gs, Utils.gs).

## Masalah yang dicegah
Pindah menu lelet karena tiap layar panggil google.script.run sendiri (~0,5-2 dtk/panggilan).
Ini kesalahan ARSITEKTUR, bukan bug. AI sering generate pola salah ini secara default.

## Patokan emas
Server dipanggil 1x saat LOGIN (bootstrap), BUKAN tiap pindah menu.
Kalau ada google.script.run jalan tiap buka layar → tanda bahaya, balik ke bootstrap.

## Pola WAJIB
1. bootstrap(token): 1 fungsi server kembalikan SEMUA data semua layar sekaligus.
   Tiap bagian dibungkus try/catch (safe()) agar role ditolak tidak gagal total.
2. Cache di client (window.API): layar baca dari cache, di-prime saat login.
   Tiap method list*/get* dibungkus cached(key, fetcher).
3. Invalidate saat mutasi: tiap save/delete/createTx → drop(key terkait).
4. Memoize getSpreadsheet_: openById 1x per request (paling mahal).
5. Render bertahap: jangan kunci seluruh layar nunggu 1 data lambat.
6. Multi-device: stale-while-revalidate — cache instan, ambil ulang diam-diam bila tua.
   Data tidak pernah hilang (cache hanya tampilan, semua tulisan langsung ke spreadsheet).

## Lantai GAS (tidak bisa dihilangkan)
Cold start ~1-3 dtk panggilan pertama saat idle. Untuk realtime sejati / kecepatan VPS
→ harus pindah Next.js + Supabase. Untuk skala kecil (1 toko), pola di atas cukup.
Jangan over-engineer.

## Prompt cepat untuk project GAS baru
"Pasang pola performa GAS dari awal (lihat rules.md): server saat login, bukan tiap pindah menu."
```
